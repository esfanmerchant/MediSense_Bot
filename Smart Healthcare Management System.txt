Smart Healthcare Management System
1. Project Objective

Build a production-quality Smart Healthcare Management System for a hospital network.

The application must provide:

Admin management
Doctor management
Patient self-service portal
Appointment management
Medical records
Prescriptions
Billing
Medical document uploads
OCR
Cloudinary storage
AI healthcare chatbot
Speech-to-text symptom input
Preliminary symptom analysis
Real-time patient vitals
Doctor alerts
Emergency access
RBAC
Audit logging
Secure authentication
Automatic 2-minute inactivity logout

The patient portal must allow patients to access their records, appointments, prescriptions, reports and billing without staff assistance.

2. Important Implementation Principle

Do not attempt to build the entire system in one step.

Codex should work in phases.

For every phase:

Inspect the existing project.
Understand the current architecture.
Create/update the implementation.
Run tests.
Run lint/type checks.
Fix errors.
Only then proceed to the next phase.

Do not rewrite working code unnecessarily.

If a technology stack already exists in the repository, preserve it unless there is a strong technical reason to change it.

11. RBAC

Implement centralized authorization middleware.

Example:

requireAuth()
requireRole("ADMIN")
requireRole("DOCTOR")
requireRole("PATIENT")

But don't rely only on role.

Also implement resource-level authorization.

Example:

PATIENT
    ↓
Can access own records only

DOCTOR
    ↓
Can access assigned/authorized patients

ADMIN
    ↓
Can manage system according to administrative permissions

Never implement authorization solely in the frontend.

12. Emergency Access

The requirements specify that an on-duty nurse may override normal restrictions during a declared emergency.

Implement emergency access as a controlled "break-glass" mechanism.

Requirements:

Emergency declared
       ↓
Authorized nurse requests emergency access
       ↓
System verifies authorization
       ↓
Require emergency reason
       ↓
Temporary access granted
       ↓
Critical patient data displayed
       ↓
Every action recorded in AuditLog
       ↓
Emergency access expires

Every emergency access event must record:

user
patient
reason
timestamp
IP
records accessed
actions performed
expiration

Do not create an unrestricted bypass.

          ↓

19. AI Safety

This is particularly important because the application deals with healthcare.

The AI must not claim to provide a definitive medical diagnosis.

Use language such as:

This information is for preliminary guidance only
and does not replace evaluation by a licensed healthcare professional.

The source requirements explicitly state that the chatbot is preliminary guidance and does not replace a doctor's diagnosis.

Implement emergency escalation.

For example, if the AI detects potentially urgent symptoms:

Potential emergency
       ↓
Show emergency warning
       ↓
Recommend immediate professional/emergency care
       ↓
Do not provide false reassurance

Do not let the model invent medications, prescriptions, or definitive diagnoses.

24. OCR Validation

Never automatically assume OCR is correct.

For example:

OCR detected:

Medicine: Amoxicillin
Dosage: 500mg
Frequency: 2/day

Show:

Is this information correct?

[Edit] [Confirm]

Only save confirmed structured information.

This is particularly important for prescriptions because OCR errors could alter medication information.

25. Cloudinary Integration

Cloudinary should store the original uploaded files.

The source requirements specify storing medical reports, prescriptions, X-rays, MRI scans, CT scans, profile images and other healthcare documents.

Architecture:

   ↓

   ↓
Cloudinary URL
   ↓
Database

Database should contain metadata and the Cloudinary reference rather than storing large files directly.

The source explicitly describes saving the Cloudinary URL and metadata in the database while the actual files remain in cloud storage.

26. Cloudinary Security

Use:

CLOUDINARY_CLOUD_NAME=

in frontend code.

Use authenticated/private delivery where appropriate for sensitive medical documents.

Do not make medical records publicly accessible merely because they have a URL.
